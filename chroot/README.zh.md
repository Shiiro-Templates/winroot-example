# chroot

`chroot` 是这个卷的语义根。它不是操作系统 chroot，也不暗示隔离。
该卷上一切有意拥有的内容都在此目录之下；Windows 在卷根创建的产物保留在它之外。

为一个条目找到归属时，首先要问的是：**谁拥有它、它扮演什么角色、它的生命周期是怎样的？**
v3 的核心是从 v2 的"按语义分类"转向"**重定向基础设施 + 按消费关系组织**"--
每个目录要么是一个重定向锚点，要么是一个有明确操作语义的归宿。不存在纯分类性质的目录。

## 顶层契约

```text
chroot/
├── Control/        # 环境控制层：环境变量、脚本、配置文件、命令日志（不装软件配置）
├── Software/       # 软件本体、配置、数据、缓存、包管理器、构建消费品
├── UserSpace/      # 用户的操作空间（Shell Folder 重定向 + 自主内容 + 凭证）
├── Projects/       # 你开发维护的项目
└── Archive/        # 暂离的材料，注意力管理工具
```

从 v2 的 8 个变 5 个：删 `Inbox`，删 `Home`（改回 `UserSpace`），删 `State`
（职责分流到 `Software/Configs` 与 `UserSpace/Vault`），`Cache` 移入 `Software/`，
`Workspaces` 改名 `Projects`。

## 核心概念

### 交付物 vs 缓存（按消费关系，不按可重建性）

- **交付物**：被直接消费的东西。即使可重建，它正在被使用。删除会破坏正在进行的消费关系。
- **缓存**：仅为避免重建/重新下载而保留、**不被直接消费**。删除只产生重建成本，不破坏消费关系。
- **判定测试**：删除后是否有正在进行的消费关系被破坏？有 -> 交付物；无 -> 缓存。
- **反例**：`target/` 完全可重建，但有自己的目录、不进统一缓存--它是正在被运行/测试的工作本体（交付物）。
  可重建 ≠ 缓存。
- **安全维度**：误标交付物为缓存 = 雷霆清理删掉正在用的资产（不可逆，危险）；
  误标缓存为交付物 = 浪费空间（可接受）。安全优先于整洁。
- **"可重建 -> 缓存 -> 忽略"是三段谬误**，每个环节独立决策，互不蕴含。

### `.pool` vs `Caches`

- `.pool` 键：（非源码 ∧ 大）。是版本控制层面的排除。
- `Caches` 键：（仅为避免重建/重下 ∧ 不被直接消费）。是消费关系层面的归类。
- 重叠：多数缓存也该 `.pool`。但两者非同集合。

### Projects vs Build2Use

- **Projects**：你**开发、维护**的源码项目。代码被版本控制跟踪，用 `.META` 装元数据。
- **Build2Use**：你**只构建来用、不维护**的源码软件。源码+构建产物是大块非源码消费品，用 `.pool` 收纳。
- 判定：这份源码你是要改它、维护它，还是只 build 出来用？前者 -> Projects；后者 -> Build2Use。
  **只使用、不维护的源码不应该放在 Projects**。

## `.pool` 与 `.META`

两个点号前缀标记目录，分工不同，通常不共存。**核心语义**：
`.pool` = "是我们的管理目标，上层有元数据"；不用 `.pool` = "不是我们的管理目标"。

### `.pool` -- 存储隔层

把一个用途分类的"管理语义"和"实际存储"分离：

```text
<用途分类>/
├── (管理语义所在，形式不约定)
└── .pool/               # 存储边界，在用途分类这层
    └── <具体工具>/       # 散装存储，无固定布局
```

- `.pool` 之上 = 管理语义所在，可被统一管理软件解析。具体形式不预先约定。
- `.pool` 之下 = 散装实际存储，不被解析。
- 统一管理软件只读 `.pool` 之上的语义，构建分类视图（如标签视图）。

**何时用**：是管理目标、且语义和存储需要分离时。如 rustup 接管的 Rust、Build2Use、Data、可重定向的应用缓存。
**何时不用**：不是管理目标时。
- 自洽官方软件单元（如 `python314`）--直接作为存储内容放在上层 `.pool` 之下，不在它内部再套 `.pool`。
- Windows 绑定文件夹（Shell Folders）--路径用 WinAPI 取，内部布局是 Windows 的，管不了。
- `Caches/Temp`--`%TEMP%` 重定向，我们只做重定向、不管内部。
- 源码项目--要被版本控制跟踪，用 `.META` 而非 `.pool`。

版本控制属性：`.pool` 同时是排除边界。原因：**它不是源码，且可能有体积问题**。不是因为可重建。
gitignore `**/.pool/`，rgignore 排除 `.pool`。

**结构化语义原则**：结构化语义永远在 `.pool` 之上，`.pool` 永远是叶子存储。

### `.META` -- 元数据目录（无 .pool 时用）

用于"内容不需要 `.pool`（源码、要版本控制跟踪），但仍需管理元数据"的场景。典型：Projects 分类层。

- 始终被 git 跟踪，始终被搜索包含。
- 内容：资产单元的分类元数据（归属、标签、状态等），具体形式不预先约定。
- **位置铁律**：`.META`（和 `.pool`）永远贴着分类层，**离资产至少一个目录的距离，绝不进资产单元内部**。
  资产单元内部（项目目录、软件目录）是它自己的世界，我们不碰。
- **按需放**，不强制每个分类层都有。
- 与 `.pool` 互补：有 `.pool` 时不建 `.META`；无 `.pool` 但需元数据时用 `.META`。两者通常不共存。

## 放置规则

1. 把软件放在其支持的安装模型允许的位置。开发工具进 `Software/Devtool/`，按用途分
   `langenv`/`ide`/`agent`；应用软件进 `Software/Apps/`，按安装方式分 `Installed`/`Portable`。
2. 不要仅仅为了让目录树看起来纯粹而拆分厂商拥有的安装结构。当软件要求文件与程序同目录时，
   就让它们留在那里。appname 用安装器/解压设的名，原样保留，不另套厂商层。
3. 软件配置进 `Software/Configs/`（与 Data 并列），不进 Control。Control 只管环境控制层。
4. 凭证进 `UserSpace/Vault/`，由 KeePass/1Password 等专门软件管，不单独顶层、不混软件配置。
5. 你开发维护的源码进 `Projects/`；只构建来用、不维护的源码进 `Software/Build2Use/`。
6. 在脚本和记录中使用 `%CHROOT_ROOT%` 而非编码盘符。
7. 顶层名称是稳定 API。仅当没有现有的所有权和生命周期分类能表示内容时，才添加新的顶层目录。

## 命名

- 结构目录使用 ASCII 英文名称和 `PascalCase`。
- 在结构目录之下，保留官方厂商/产品名称或安装器/解压设的目录名。
- 用户控制的命名空间内（如 `Devtool` 内的 `langenv`/`ide`/`agent`、`Projects` 内的分组、项目、脚本）
  可用小写/snake_case。

参见每个顶层目录的 `README.zh.md` 以了解其本地契约。`TREE.zh.md` 是简洁的参考树。
